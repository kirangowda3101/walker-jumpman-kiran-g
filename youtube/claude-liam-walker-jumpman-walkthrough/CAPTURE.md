# CAPTURE — how the gameplay in this film was recorded

**Game:** walker-jumpman-kiran-g (extension of [nikbearbrown/walker-jumpman](https://github.com/nikbearbrown/walker-jumpman))
**Engine:** Godot 4.7.2.stable.official.ed1daf0bf
**Machine:** macOS 15, Apple M4, OpenGL API 4.1 Metal — Compatibility renderer (`gl_compatibility`)
**Captured:** 22 September 2026

Every frame of gameplay in this film is a real engine run. Nothing is
re-created, re-drawn, re-tinted, animated, or reconstructed.

---

## 1. The source snapshot

`build_id` in `coverage.json` is a SHA-256 of a manifest of the game source,
not of any one file. Method, reproducible from the repository root:

```bash
find godot -type f -not -path '*/.godot/*' | LC_ALL=C sort | xargs shasum -a 256 > manifest.txt
shasum -a 256 manifest.txt
```

    build_id  f115c6bda779d53a8531bdb2a29323a609a8b217a386893c92f848f656544771
    git rev   1d68ddfcc4126be601e4a2ed9f3c53c1f4cbb314

The manifest covers all 21 files under `godot/` (scripts, scene, level JSON,
`project.godot`, `.uid` files), excluding the `.godot/` engine cache. If any
game file changes, the build id changes and every capture in `coverage.json`
becomes stale.

## 2. Isolation

The game source under `godot/` was **not modified for this film.** Capture ran
against an `rsync` copy of `godot/` in a session scratch directory, with one
added file — `capture_driver.gd` — that lives only in the copy. That driver is
committed here as `capture/capture_driver.gd` so the runs can be reproduced and
audited.

The game writes nothing to `user://` and makes no network calls, so no further
sandboxing was required.

## 3. Input: the real path, not the test hooks

`godot/tests/route_driver.gd` drives the engine's own test suites through
`player.test_control` / `test_axis` / `test_jump_pressed`. Those are
**test-only gameplay shortcuts** and were deliberately not used here.

The capture driver uses the game's real input:

| Input | Mechanism | Consumed by |
|---|---|---|
| A / D held (move) | `Input.parse_input_event(InputEventKey)` + `Input.flush_buffered_events()` | `player.gd` → `Input.get_axis("move_left","move_right")` |
| Space (jump) | same | `player.gd` → `Input.is_action_just_pressed("jump")` |
| Enter / Esc / P / R / M | `SubViewport.push_input(InputEventKey)` | `session.gd::_unhandled_input` |
| Left mouse on START | `SubViewport.push_input(InputEventMouseMotion + MouseButton)` | `session.gd::_unhandled_input` |

The two paths do not overlap: nothing polls the discrete UI actions and nothing
in `_unhandled_input` handles movement, so no input is delivered twice.

The driver **never** writes `position`, `velocity`, `state`, `deaths`,
`elapsed` or completion, never disables collision, and never calls a test hook.
It **does read** `player.position`, `player.velocity` and `game.state` to decide
*when* to press a key — the same information a human watching the screen has.
One helper, `predicted_ticks_to_y()`, forward-integrates the fall using the
game's own `tuning.gd` constants so the input-buffer press can be timed five
ticks before contact. That chooses a moment; it does not change one.

**These are scripted-input captures, labelled `scripted-input` in
`coverage.json`. They are not a human playtest**, and nothing in this film
claims otherwise. The only human play evidence for this project is the author's
own, recorded in `TEST-REPORT.md` section 5.

### Jump marks

`run-01` uses the ten marks already committed in `godot/tests/route_driver.gd`,
which were generated by `scripts/solve.py marks` and verified in the engine.

`run-03`'s eastern marks (1180, 1311, 1439, 1559, 1724) were authored for this
film with a scratch script over the project's own simulator (`scripts/sim.py`),
and each was required to still survive at ±3 px of jitter. That tolerance is
deliberate: `TEST-REPORT.md` section 2 records that tick-exact marks completed
in the simulator and then died in the engine.

### Two accommodations, both declared

1. **`is_on_floor()` flicker.** Running along a flat slab, the engine drops
   `is_on_floor()` for isolated frames. `jump_at()` therefore treats "grounded"
   as "touched the floor within the last 3 ticks" — the same tolerance the
   game's own 6-tick coyote window gives the player. Without it, a mark can be
   skipped and the take dies against the next wall.
2. **`test_mode` during unattended capture.** `session.gd` pauses on window
   focus loss. For `run-01` to `run-04` the driver sets `game.test_mode = true`,
   which disables *only* that auto-pause, so a stray OS focus change cannot
   corrupt a take. `run-05` leaves `test_mode = false` and demonstrates the real
   behaviour on camera: a second engine `Window` grabs focus, the root window
   emits `focus_exited`, and the game pauses itself. That is a genuine engine
   focus change, not a synthesised signal.

## 4. Resolution: native 4K, and what that means here

`project.godot` declares a **640×360 logical canvas** with
`display/window/stretch/mode="canvas_items"`. This machine's display is
3024×1964, so a 3840×2160 OS window would be clamped by macOS and Godot's Movie
Maker would have written a smaller frame.

Instead the session runs inside a **3840×2160 `SubViewport`**, which is a render
target and is not display-clamped. `Camera2D.zoom = 6` and a 6× transform on the
HUD `CanvasLayer` reproduce exactly what `canvas_items` stretch does at that
window size, so the framing is identical to a normal 640×360 run — no extra
world is revealed and no geometry was moved to fill the frame.

**Every visual in this game is a vector `draw_rect` / `draw_line` /
`draw_colored_polygon` / `draw_string` call.** There are no bitmaps and no
sprite sheets. Rendering the same canvas at 6× is therefore genuine 4K
rasterisation, not an upscaled recording. Disclosed plainly: **logical canvas
640×360, rendered natively at 3840×2160.**

## 5. Frames and encoding

Physics runs at 60 Hz under `--fixed-fps 60`; every second physics tick is saved
as a PNG from `SubViewport.get_texture().get_image()`, giving **30 fps at
real-time speed**. No frame is dropped, duplicated, interpolated or re-ordered.

```bash
Godot --path <capture-copy> --script res://capture_driver.gd \
      --fixed-fps 60 --resolution 1280x720 -- <run-id> <out-dir>

ffmpeg -framerate 30 -i <run-id>-frames/%06d.png \
       -c:v libx264 -crf 14 -preset slow -pix_fmt yuv420p -r 30 -movflags +faststart <run-id>.mp4
```

`--resolution 1280x720` sizes the throwaway host window only; nothing is
rendered from it. The captures are 3840×2160, 30 fps, and their SHA-256 hashes
are recorded in `coverage.json` — changing a capture invalidates its evidence.

## 6. Input logs

Every run writes `capture/<run-id>-inputs.jsonl`, one JSON object per event:
tick, seconds, position in the finished video, event kind, action, key, game
state, player x/y, `on_floor`, axis, `velocity.x`, retry count and elapsed
time. `note` rows mark what the driver asserted at that moment. The logs are the
timing evidence for the coyote-window and input-buffer beats, where a still
frame cannot establish causality.

## 7. Audio

**The game has no audio of any kind** — no music, no sound effects, no audio
files anywhere in the project (`SOURCES.md`: "no audio"). Nothing was muted,
because there was nothing to mute, and no sound effects were invented for the
film. Liam's Kokoro narration is the only audio track. The outro card is spoken
over silence with a 1 s tail hold; there is no jingle.

## 8. Takes

Every take in the film ran green — the driver asserts its expected outcome at
each step and exits non-zero otherwise. Takes that failed during authoring were
re-run after fixing the *driver*, never the game:

| Failure | Cause | Fix |
|---|---|---|
| `run-03` died in the third gap | braked mid-air before clearing the 40 px gap | removed the brake; the 32 px headroom at x=1060 is cleared on foot anyway |
| `run-03` died at the fourth spike cluster | marks copied from the optimal solver path; the runway overhead cuts the arc short | re-derived marks with ±3 px jitter tolerance |
| `run-04` missed a jump mark | `is_on_floor()` flicker | 3-tick grounded tolerance |
| `run-04` buffered jump did not fire | a late coyote jump lands flush against the block at x=576, and whether the next jump cleared it was a one-frame coin flip | back off west first for a full-speed run-up |
| `run-01` became nondeterministic | the west-boundary demo shifted the phase of every downstream jump mark | moved that demo into `run-04` |

`run-01` through `run-05` were each run twice consecutively and produced
identical tick and frame counts before being encoded.
